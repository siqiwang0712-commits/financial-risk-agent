# v0.3.3 — Shared Limits, Secret Mounts & Honest Failure Diagnostics

**Version:** `0.3.3` · **Date:** 2026-09-19 · **Status:** release candidate, all gates
verified locally (production deployment remains unvalidated).

v0.3.2 hardened replay semantics and PostgreSQL runtime selection. This release closes
the operational gaps that only appear once the stack is actually operated: a rate limit
that survives restarts and replicas, secrets that can be mounted instead of exported, a
database healthcheck that tells the truth about a rotated password, and a readiness
probe that names the failure instead of hanging on it.

Nothing in `research/` changed. E1/E2/E3 and `research/results/public_v1` remain
byte-for-byte frozen historical evidence and are not regenerated by current code.
Predictive superiority and probability calibration remain not established.

## Upgrade path (v0.3.2 → v0.3.3)

Migrations are additive and idempotent. `005_shared_rate_limit.sql` creates
`rate_limit_events` and `006_rate_limit_retention.sql` adds its retention indexes; no
existing table, column or row is modified. Upgrading a v0.3.2 database that already
holds organisations, entities, documents, snapshots, decision bundles, risk snapshots
and audit history was verified end to end: every pre-existing table fingerprint is
identical before and after, all of it stays readable through the repository, and a
second run of the whole migration set changes nothing.

With the production overlay the one-shot `migrate` service applies them before the API
starts:

```bash
POSTGRES_PASSWORD='<strong-secret>' docker compose -f docker-compose.yml -f docker-compose.prod.yml up --build
```

With the development stack migrations are applied on boot (`FINRISK_AUTO_MIGRATE=1`).
They can also be applied and validated out of band:

```bash
$env:PYTHONPATH="backend"
$env:DATABASE_URL="postgresql://finrisk:<secret>@host:5432/finrisk"
python scripts/validate_postgres_migration.py
```

`scripts/validate_postgres_migration.py` is idempotent and is safe to re-run on every
deploy. Run it before the test suite on a fresh database: the suite assumes the schema
already exists and does not create it, and without `rate_limit_events` the limiter fails
closed so every authenticated route answers 503.

## Rotating the database password

`POSTGRES_PASSWORD` is only applied when the PostgreSQL volume is **first** initialised.
If the configuration is changed against an existing volume, the server keeps the old
credential and every application connection is rejected. **How that surfaces depends
entirely on whether the API is already running** — the two cases behave differently and
must not be described with one blanket statement.

**Case A — a running API** (the database credential changes underneath it). The process
stays up, so the liveness route is unaffected:

- `/health/live` → `200` (the process is alive; this route never touches the database);
- `/health/ready` → `503` naming the rejected credential, with `Retry-After`.

This is *not* instantaneous. PostgreSQL does not terminate established sessions, so an
API holding pooled connections keeps answering `200` until those sessions break — a
restart, a pool grow, or a lifetime expiry. A `200` immediately after an `ALTER USER`
is not evidence that the rotation was safe.

**Case B — a cold start against a mismatched credential.** There is no running API to
answer anything:

- the PostgreSQL container reports `unhealthy` — the probe authenticates against the
  container's own address on the Compose network, not `127.0.0.1`, which the image's
  `pg_hba.conf` trusts and therefore accepts with any password; under Compose the API
  is gated on `service_healthy`, so `up` can stop before the API container is created;
- if the API does start, it builds its connection pool while the app module is imported
  and that readiness wait gives up after 10 s with `psycopg_pool.PoolTimeout`, so the
  container exits and **`/health/live` and `/health/ready` are both unreachable**.

So the shorthand "wrong password → `/health/live` always remains 200" is **false**:
it holds only for Case A. In Case B neither route answers at all.

Rotate inside the database first, then update the configuration:

```bash
docker compose exec postgres psql -U finrisk -d finrisk -c "ALTER USER finrisk WITH PASSWORD '<new-secret>'"
```

Service recovers without a rebuild. Recreating the volume with `down -v` also works but
**destroys the stored data**.

## Mounting secrets instead of exporting them

`DATABASE_URL_FILE` and `FINRISK_BOOTSTRAP_TOKEN_FILE` take the secret from a mounted
file, so it stays out of `docker inspect` output and out of the process environment. The
file wins over the environment variable when both are set. A configured-but-unreadable
file (missing path, or unreadable) raises instead of silently falling back; only an
*empty* file falls back to the environment variable, which is what an unmounted or
not-yet-populated secret looks like in practice. The one-shot migration service
resolves `DATABASE_URL_FILE` identically — the production overlay passes the variable to
it too, so a deployment that mounts the DSN works on every service or fails loudly on
all of them rather than migrating one database while the API serves another.

`/health/ready` verifies that the required v0.3.3 schema sentinels are present, not
merely that PostgreSQL accepts a connection. It looks up seven runtime database
objects — `organizations`, `entities`, `analysis_snapshots`, `audit_events`,
`rate_limit_events`, `idx_rate_limit_events_lookup` and `idx_rate_limit_events_expiry`
— in one `to_regclass` round trip, so an un-migrated or partially migrated database
answers `503` with `Retry-After` instead of a misleading `200`. All seven present is
reported as `schema: "complete"`. `/health/live` is unchanged and still means only
"the process is up", which is what a restart policy should key off.

These seven objects are **sentinels, not a full schema audit**: the probe proves that
the required objects exist, not that every column, constraint and index definition
matches the migrations. Verifying the migrations themselves — including the v0.3.2 →
v0.3.3 upgrade, idempotency and zero drift — is the job of
`scripts/validate_postgres_migration.py`, which runs as the one-shot `migrate` service
before the API starts in the production overlay.

## Datastore outage response

A database that stops answering is reported in seconds rather than after the pool's
30-second default, and concurrent requests do not queue behind each other while it is
down: twenty simultaneous authenticated requests were each answered in about five
seconds, wall clock included, where serialising them would have taken about a hundred.

Three optional settings control this; each falls back to its default on an empty,
negative or unparseable value, and none of them touches the 60-second analysis timeout.

| Setting | Default | Meaning |
|---|---|---|
| `FINRISK_DATABASE_OPERATION_TIMEOUT_SECONDS` | `5.0` | How long a request waits for a pooled connection before the API answers a controlled `503`. |
| `FINRISK_DB_RECONNECT_TIMEOUT_SECONDS` | `5.0` | Ceiling on one pool reconnection chain (the library default is `300`), so a failing peer cannot pin every request to a single long attempt. |
| `FINRISK_DB_CONNECT_TIMEOUT_SECONDS` | `5` | libpq handshake ceiling. Without it, a peer that accepts the socket and then never replies holds a connection for as long as the OS allows — measured at ~130 s, and the reason pool recovery used to take minutes. |

Outages answer `503` with `Retry-After: 5` and the caller's correlation id, never `500`,
never a traceback, and never an unauthenticated pass. Readiness and business traffic
recover by themselves once the database returns; no restart and no data loss.

## Rate limiting

When PostgreSQL is in use, rate limits live in `rate_limit_events` rather than in one
process, so the window survives a restart and is shared across replicas. Admission is
serialised per key with a transaction-scoped advisory lock. Expired rows are swept in
bounded batches, and a hard row cap (`FINRISK_RATE_LIMIT_MAX_ROWS`, default 200000)
bounds a flood of unique keys.

The cap is a **fail-closed bound, not a trimming one**. Sweeps delete expired rows only;
a row that is still inside its window is the record of quota a client has already spent
and is never discarded. When live rows fill the table there is nowhere safe to put a new
event, so the limiter raises `RateLimiterUnavailable` and the API answers `503` with
`Retry-After` and the caller's correlation id rather than silently restoring a quota that
was legitimately exhausted. Capacity returns on its own as rows age out — no restart and
no manual sweep. If the store is unavailable the limiter also fails closed: `503`, never
an unauthenticated pass.

Provision the cap above the expected working set. Setting it far below the live working
set is a configuration error, and it now surfaces as capacity-pressure `503`s instead of
quietly evicting live events.

## LLM provider

`FINRISK_LLM_PROVIDER=openai` (or `openai-compatible`) drives the schema-constrained
`StructuredLLMProvider` against an OpenAI-compatible endpoint. The request shape, the
`Authorization` header, the JSON-schema constraint, retry on a transient `5xx` and the
handling of the response were verified against a local OpenAI-compatible endpoint.

The full chain was additionally exercised once against a real hosted provider, end to
end: `FinancialRiskAgent → StructuredLLMProvider → HTTPS → ChatAnywhere → GPT-5 →
structured response → schema validation → assessment → persistence`, including a real
Chromium upload whose result was rendered from a real model verdict. The endpoint
accepted the project's `response_format` JSON schema with `strict=true` natively, so no
compatibility shim was needed and no schema validation was relaxed. On this path the
provider is explicit: `FINRISK_LLM_PROVIDER` was never `mock` and no run fell back to it.

The credential used for that run was injected at runtime only, and a full-repository,
full-history, container-inspect and artifact scan after the run found zero occurrences of
it. No key is shipped, referenced or required by this release. Results are recorded as
observed on the date of preparation; latency, token usage and cost for any hosted
provider are that provider's to change.

### Final freeze verification (2026-09-19)

The hosted path was re-verified once more, minimally, on the final v0.3.3 file state:
model discovery from the provider's own `/v1/models`, one direct `StructuredLLMProvider`
call, and one `PDF → FinancialRiskAgent → GPT-5 → decision` run. **30 of 30 assertions
passed** — `provider=openai-compatible`, `model=gpt-5`, `schema_valid=true`,
`prompt_version=narrative-v1.1.0-claim-conditioned`, non-zero token usage on every real
call, the LLM claim present as a `claim` node in the assessment's evidence graph and
counted in `verified_claim_coverage`, and `mock` occurring **zero** times anywhere in the
response or its telemetry.

One observed caveat, recorded because it is real: the hosted endpoint does not always
return schema-valid JSON. On one run it did not, and the software **failed closed** —
`LLM_narrative` recorded `failed`, the run ended `REVIEW_REQUIRED` with decision
`REVIEW`, and nothing degraded to `mock`. A retry succeeded.

> **The validation credential must be revoked/rotated before production use.** It was
> supplied as a temporary runtime secret for this verification and it appeared in
> cleartext in the conversation that requested the run; no rotation was performed on the
> issuer's side and none can be evidenced from here. The post-run scan covered 360
> tracked files, 2 untracked files, all three `git diff` views, `git reflog`,
> `git stash`, 9 204 workspace artifacts (including `node_modules`, `.next` and the
> virtualenv) and every container environment: **zero occurrences**. That is evidence the
> repository does not carry the key, not evidence the credential is safe to keep.

## Limitations carried forward

Production deployment remains unvalidated — every result above comes from a local stack
or a single hosted-provider run on the date of preparation, not from a live multi-tenant
installation. No external validation or regulatory approval is claimed.

The hosted-provider results are a **point-in-time observation**: they evidence that the
software's own path works against a real model, not any guarantee about that vendor's
availability, latency, cost or model behaviour. A missing or rejected credential fails
closed rather than degrading to `mock`.
